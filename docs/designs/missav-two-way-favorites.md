# MissAV 官网双向同步与插件取消回写设计（MVP）

- Status: APPROVED
- Date: 2026-08-28
- Owner: SamLiu
- Branch: main
- Scope: MissAV only

## 1. 决策摘要

第一版采用 B 方案：在 MissAV 影片详情页的主页面上下文中复用官网现有 Axios 请求，并通过受限的 `window.postMessage` 桥接到扩展内容脚本。

MissAV 官网始终是收藏状态的唯一事实来源：

- 官网收藏请求完成且复查确认“已登录 + 已收藏”后，本地新增或更新该影片。
- 官网取消请求完成且复查确认“已登录 + 未收藏”后，本地删除该影片。
- 插件管理页取消收藏时，必须先让官网取消成功并再次确认状态，之后才能删除本地数据。
- 全量同步只有在全部页面抓取、解析和校验成功后，才用官网快照精确替换本地 MissAV 收藏；任一页失败都保留旧数据，不执行删除对账。

第一版不重做通用同步内核，不改 Jable，不新增标签、账号系统或云同步。

## 2. 为什么现在做

### 用户问题

核心用户已经在 MissAV 收藏了大量影片，但官网收藏没有形成好用的整理和再发现体验。插件目前只能手动从 `/saved` 页把数据追加进本地：

- 官网后来新增或取消的收藏不会实时反映到插件。
- 插件里删掉一条记录只会删本地，官网仍然保留，下一次同步又会回来。
- 全量同步只做 upsert，不会清理官网已经取消的记录。

这导致插件无法成为可信的收藏管理器。

### 需求证据与风险

已有的需求证据较弱：项目在 GAV Bus 论坛发布后有人安装，但尚无用户访谈、付费或高频反馈。当前最可靠的需求来源是作者本人长期使用 MissAV/Jable 后的痛点。

因此本次投入必须保持窄：只验证“可靠的 MissAV 收藏闭环是否足以成为付费产品的核心价值”，而不是提前建设完整同步平台。

## 3. 已确认的产品规则

1. MissAV 官网是唯一事实来源。
2. 官网发生收藏或取消时，本地在官网请求完成并复查真实状态后立即跟随。
3. 插件发起的取消操作必须远端优先；官网失败时本地不得变化。
4. 全量同步成功后，本地必须与官网收藏集合完全一致。
5. 全量同步出现部分失败、登录失效、页面结构异常或数量校验异常时，不得删除本地数据。
6. 第一版仅处理 MissAV 收藏，不影响 Jable 的收藏/稍后观看逻辑。

## 4. 浏览器实测结果

在用户已登录的 MissAV 影片页和收藏页进行了只读检查，没有触发收藏或取消操作。

所检查的影片页使用 Alpine 风格的 `x-data` 状态和页面内 Axios：

- `GET /api/items/{opaqueItemId}/view`：返回用户和当前收藏状态。
- `POST /api/items/{opaqueItemId}/save`：收藏。
- `DELETE /api/items/{opaqueItemId}/save`：取消收藏。

示例影片 `hmdnv-727` 对应的内部标识是另一个不透明值，二者不能互相推导。在当前已检查路径中，只在详情页 HTML 的 `x-data` / `x-init` 发现了可靠映射，尚未发现可只凭本地番号调用的公开映射接口。因此第一版需要复用或打开对应详情页，不能直接拼 API。

请求是当前页面同源请求。实现不得读取、复制或持久化用户 Cookie；由页面上下文中的 Axios 自然携带当前会话。域名必须从当前页面派生，并限制在 `missav.ws`、`missav.ai`、`missav.live`，不能写死 `.ws`。

收藏页实测有 146 页。现有逐页固定等待 3 秒的同步需要约 7 分钟以上，且当前只追加不对账，因此全量同步需要单独的“先完整收集、后原子替换”路径。

## 5. 第一版用户体验

### 官网操作

1. 用户在任意受支持 MissAV 详情页点击官网原生“收藏”。
2. 官网的 POST 请求完成后，扩展把它当作“需要复查”的候选事件，而不是成功事实。
3. 扩展调用 GET `/view`；只有同时满足 `user` 明确存在且 `saved === true`，才确认收藏成功。
4. 扩展抓取当前详情页已有的标题、番号、封面、预览地址和规范 URL，写入本地 MissAV 收藏；元数据不完整时至少保存 `videoId + URL` 的最小可恢复记录。
5. 用户在插件管理页能立即看到该条目，无需手动全量同步。

取消收藏同理：只有 DELETE 完成后又确认“已登录 + `saved === false`”，扩展才从本地删除对应条目。未登录、字段缺失或非布尔值一律是 unknown，不得改变本地。

这个实时闭环只覆盖安装了扩展的当前 Chrome 中打开的详情页；其他浏览器、移动端或扩展未运行期间发生的变化，由下一次全量同步补齐。

### 插件管理页操作

1. MissAV 卡片新增“从官网取消收藏”按钮。
2. 点击后按钮进入处理中状态，卡片暂时保留。
3. 后台复用或打开一个不激活的详情页，由页面上下文读取真实状态。
4. 只有 GET 同时确认已登录且未收藏才视为成功；若确认已登录且仍收藏，发送 DELETE，再用 GET `/view` 确认结果。
5. 只有确认官网为未收藏后，才删除本地卡片。
6. 登录失效、页面结构变化、请求失败或确认超时，均保留本地卡片并显示可操作错误。

### 第一版刻意不做的入口

插件管理页目前没有“未收藏影片目录”，因此第一版不提供“从插件重新收藏一个已不存在的条目”入口。这不影响协议层支持 POST；未来若引入历史归档、回收站或站内搜索，可直接复用同一远端收藏命令。

因此 MVP 的准确名称是“官网双向同步 + 插件取消回写”。协议层支持未来 POST 回写，但产品层尚不宣称“插件可发起收藏”。如用户要求完整的插件收藏入口，必须先批准历史归档/回收站这一额外产品模型。

## 6. 技术设计

### 6.1 页面主上下文 Hook

新增 `content-missav-detail-hook.js`，作为 manifest 静态内容脚本，以 `run_at: "document_start"`、`world: "MAIN"` 注入；manifest 设置 `minimum_chrome_version: "111"`。静态 manifest 的 ExecutionWorld 从 Chrome 111 起可用；这避免动态 script 标签受页面 CSP 和加载时序影响。Chrome 官方文档确认静态内容脚本支持 `world: "MAIN"`，且 `document_start` 发生在页面其他脚本之前。

- 同时包装 `XMLHttpRequest.prototype.open/send` 和 `window.fetch`；当前页面代码使用 Axios，但传输 adapter 未经实测，不能只假设 XHR。
- 只匹配允许域名下、路径严格符合 `/api/items/{opaqueItemId}/save` 的 POST 和 DELETE。
- 请求完成后只发出 `operationCandidate`，绝不直接触发本地变更；网络失败或非 2xx 也只产生 unknown 结果，便于显示错误。
- 事件只包含操作类型、规范化路径和必要的关联 ID，不包含 Cookie、Authorization、响应正文或用户标识。
- 接收扩展命令时，只从当前 `location` 和 DOM 自行派生影片身份与 endpoint，不接受消息传入任意 URL/内部 ID；等待 DOM endpoint 与 Axios ready，再用页面已有 `window.axios` 执行同源 GET/POST/DELETE。
- 非影片页、endpoint 缺失/重复、Axios 不可用或响应 schema 不明确时 fail closed。

不依赖按钮文案或 CSS 类来判断收藏状态，避免语言切换和样式调整导致误判。官方依据：[Chrome content scripts manifest](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts) 和 [chrome.scripting ExecutionWorld](https://developer.chrome.com/docs/extensions/reference/api/scripting)。

### 6.2 统一验证状态机

官网原生操作和插件命令必须共用同一验证器，避免插件发出的 DELETE 被观察器提前当成成功：

- 每个 `opaqueItemId` 维护递增 generation；每个候选事件只触发一次延迟复查。
- 复查结果只有三态：`authenticated_saved`、`authenticated_unsaved`、`unknown`。
- `response.data.user` 必须明确表示已登录，且 `saved` 必须是布尔值，才能进入前两态；其余全部是 unknown。
- 每次 GET 返回后再次检查 generation；若期间出现更新事件，丢弃旧结果并复查最新状态。
- 快速“收藏→取消”、请求乱序和插件命令产生的观察事件最终只提交最新的已验证状态。
- 后台只接受 `verifiedState`，不接受 POST/DELETE 2xx 直接写本地。

插件命令的 Promise 也只有在自己的变更请求完成、并且统一验证器确认目标状态后才成功。`DELETE 2xx` 但复查仍为收藏时，命令失败且本地逐条不变。

### 6.3 隔离世界内容脚本

新增 `content-missav-detail.js`：

- 校验 `window.postMessage` 的 `source`、消息命名空间、requestId 和允许操作。requestId 只用于关联与去重，不作为安全凭据；同页脚本能读取或重放 nonce。
- 收到已验证状态后，从当前 `location` 和 DOM 自行提取影片身份；不信任消息内传入的任意 URL/videoId。
- `authenticated_saved` 时向后台发送单条 upsert；`authenticated_unsaved` 时请求后台删除；unknown 不写本地。
- 接收后台的远端状态变更命令，转发给 Hook，并把带 requestId 的结果返回后台。

页面到扩展的消息必须是显式 allowlist；后台还要校验 `sender.tab.url` 与消息派生身份一致。其他页面脚本伪造的任意 URL 或任意后台 action 不得透传。

### 6.4 后台协调

在 `background.js` 中增加 MissAV 专用协调逻辑，不抽象成跨站通用同步框架：

- `normalizeMissavUrl(url)`：保留当前受支持域名，去除无关 query/hash，兼容语言前缀。
- `findOrCreateMissavDetailTab(url)`：优先复用已打开详情页，否则新建不激活标签页；等待内容脚本 ready，并设置超时。
- `setMissavFavoriteRemotely(url, desiredSaved)`：远端三态读取、幂等比较、必要变更、统一验证。
- `removeMissavFavoriteRemotely(url)`：`desiredSaved=false` 的 UI 入口；确认成功后调用本地删除。
- 网站观察事件使用单条 upsert/delete；重复事件必须幂等。

扩展创建的临时标签页在任务结束后关闭；复用用户已有标签页时不关闭、不导航。若 URL 域名不在允许列表，立即拒绝。

每个后台操作写入 `chrome.storage.session` 的最小 pending 记录（requestId、操作类型、tabId、目标规范 pathname 的本地哈希、是否为扩展创建、deadline，不含影片标题/番号）。MV3 service worker 重启后只在当前 tab URL 的 pathname 哈希仍匹配时恢复查询，不把未知结果当成功。关闭扩展创建的超时标签页前还要确认它没有被用户激活且未发生导航；否则只放弃扩展所有权并保留标签页。

若官网已确认变化但 IndexedDB 写入失败，向用户显示“官网已变化，本地待修复”，保留可重试 repair 标记，并允许全量同步恢复，不能谎报完全成功。

### 6.5 全量精确同步

改造 `content-missav.js` 和后台存储接口：

1. 每次抓取前先通过明确的登录标志验证会话，记录目标路径、总页数与首页指纹。
2. 按页抓取，任一响应非 2xx、重定向到非 saved 路径、解析异常或页数漂移即本轮失败。
3. 每页先用宽匹配统计候选卡片容器，再逐条解析。候选数必须等于成功解析数；每条必须有受支持的详情 URL 和稳定 `videoId`，页内与跨页不得重复。
4. 分页必须能枚举连续的 `1..N`；非末页候选数必须符合本轮稳定页容量，末页不得超过该容量。若页面展示总收藏数，解析后的唯一集合数必须与它一致。
5. 只有明确匹配 saved 页面身份、分页结构和登录态才允许非空快照；只有明确匹配官网空态组件且无分页时才允许空快照。任一结构契约无法证明完整时 fail closed。
6. 连续执行第二轮完整抓取；只有两轮都通过上述结构契约，且登录状态、页数、逐页候选数和 `videoId` 集合完全一致，才把它定义为“稳定完整快照”。
7. 两轮不同但两轮各自结构完整时，只用时间更晚的第二轮集合执行幂等 upsert，不允许删除差集，并提示用户重试；任何一轮结构不完整则本地完全不变。
8. 将稳定完整快照一次性发送给后台 `replaceMissavFavorites`。
9. 后台在单个 IndexedDB readwrite transaction 中完成旧物理 key 清理、put 与删除差集。
10. transaction 完成后才上报成功；失败则原有集合保持不变。

空收藏集合只有在确认已登录、分页/空状态页面结构有效时才允许替换为空，避免登录页或风控页被误判成“零收藏”。

当前固定 3 秒节流会让 146 页双轮校验超过 14 分钟。实现改为单并发、可中断、带进度的自适应节流：默认短间隔，遇到 429/5xx 指数退避；不以提高并发换取风控风险。实际间隔在只读请求回归后确定并记录。

由于官网没有已知的服务端 snapshot version，这不是数学意义上的原子快照；两轮结构完整且集合一致是第一版允许执行删除对账的保守门槛。若仍频繁检测到漂移，产品应退回“只新增更新，不自动删除”，而不是降低校验。

### 6.6 数据身份

本地 MissAV store 当前以 URL 为 keyPath，而同一影片可能因域名或语言前缀产生不同 URL。第一版不立刻迁移 store keyPath，但所有写入和删除都先提取稳定 `videoId`：

- 单条 upsert 在同一个 readwrite transaction 中用 cursor 枚举相同 `videoId` 的全部物理 key，删除旧域名/语言 URL 后再写一条规范记录，防止跨域重复和并发竞争。
- 删除在同一个 transaction 中删除匹配规范 URL 或 `videoId` 的全部物理 key。
- 全量替换按 `videoId` 做集合对账。

后续若真实用户数据证明跨域重复频繁，再单独做 IndexedDB schema migration，把 `videoId` 改为主键。

## 7. 失败语义与一致性

| 场景 | 官网状态 | 本地动作 | 用户反馈 |
|---|---|---|---|
| 官网 POST/DELETE 完成，GET 明确已登录且确认最终状态 | 已确认 | 跟随 upsert/delete | 静默成功 |
| 官网请求失败或 GET 三态为 unknown | 未确认 | 不变化 | 保留本地，可重试 |
| 插件取消，GET 明确已登录且显示已取消 | 已取消 | 删除本地 | 成功 |
| 插件取消，DELETE 后复查已取消 | 已取消 | 删除本地 | 成功 |
| 插件取消超时/非 2xx/复查仍收藏 | 未确认或未变化 | 保留本地 | 明确报错，可重试 |
| 全量抓取任一页失败 | 未知 | 不做替换 | 同步失败，旧数据保留 |
| 两轮结构完整且集合一致 | 稳定快照 | 原子精确替换 | 显示新增/删除/总数 |
| 两轮结构完整但集合不一致 | 抓取期间可能变化 | 仅 upsert 第二轮，不删除 | 提示发生变化并重试 |
| 任一轮结构契约不完整 | 可能稳定漏解析 | 完全不写本地 | 提示站点结构可能变化 |

不做乐观本地删除。页面上的 Alpine 状态会在请求发出时立即翻转，因此按钮视觉状态和网络 2xx 都不能单独作为成功依据，只有已认证的 GET `/view` 三态结果可以驱动本地变更。

## 8. 安全与维护边界

- 只允许 HTTPS 和三个明确 MissAV 域名。
- 不读取或记录 Cookie、localStorage、账号 ID、请求头和响应正文。
- 不暴露通用网络代理能力；主上下文只接受固定收藏协议。
- 不通过 DOM 自动点击收藏按钮。
- 所有解析器对缺失/多重 endpoint 采取 fail closed。
- 外部遥测默认关闭或经用户明确同意后启用；只发送聚合动作、结果、耗时和错误类别。影片标题、番号、URL、opaque ID、账号状态及收藏内容不得发送到 Amplitude 或其他外部服务。
- MissAV 接口是未公开页面内部协议，随站点升级可能变化；解析失败必须退化为“保留本地并提示重新全量同步”，不能猜测 endpoint。

## 9. 代码变更范围

预计涉及：

- `manifest.json`：补齐三个域名的 host permissions，以 MAIN/ISOLATED 两个静态 content script 注册详情页逻辑并声明最低 Chrome 111；不再依赖 web accessible 动态注入。
- `content-missav-detail-hook.js`：主上下文网络观察与远端状态命令。
- `content-missav-detail.js`：消息桥、DOM 元数据提取、后台通信。
- `content-missav.js`：全量抓取校验与完整快照提交。
- `background.js`：远端优先协调、幂等验证、精确替换 transaction、跨域身份归一化。
- `options.js` / `options.html`：MissAV 取消按钮、pending 状态和错误提示。
- `pack.sh`：加入两个新增脚本。
- 测试文件：endpoint 解析、消息校验、URL 归一化、幂等状态机、全量替换和失败保留。

明确不改：Jable 详情页 Hook、Jable 收藏/稍后观看数据模型、付费系统、云端服务。

## 10. 验收标准

### 功能

- 在 `.ws`、`.ai`、`.live` 任一受支持详情页，官网收藏经 GET 复查成功后本地在 2 秒内出现对应条目。
- 官网取消经 GET 复查成功后本地在 2 秒内移除对应条目。
- 插件管理页取消操作只有在官网已确认未收藏后才移除卡片。
- 重复收藏、重复取消、页面刷新和重复网络事件不会产生重复记录或错误删除。
- 语言前缀 URL 和跨域 URL 不会为同一番号生成多条本地记录。
- 退出登录或接口失败时，插件不删除本地数据，并给出可理解的错误。
- DELETE 返回 2xx 但复查仍为收藏时，本地对应条目逐字段保持不变。
- 未登录响应即使包含 `saved=false` 也归类为 unknown，本地逐条保持不变。
- 快速收藏→取消及 GET 乱序回包最终只应用最新已验证状态。
- 官网已变化但 IndexedDB 写入失败时，界面显示待修复状态，并能通过重试或全量同步恢复。
- 元数据不完整时仍保存 `videoId + URL` 最小记录。
- 两轮结构完整且集合一致后，本地 MissAV `videoId` 集合与官网快照完全一致。
- 全量任一页失败时，本地集合逐条保持不变。
- 两轮稳定漏解析同一批候选卡片时，因为候选数与成功解析数不等，不得删除任何本地记录。
- MV3 service worker 中途重启时，不把 pending 操作当成功，且最终清理扩展创建的临时标签页。

### 测试

- 用保存的最小 HTML fixture 测试 Alpine endpoint 解析，覆盖语言前缀、属性顺序变化和缺失 endpoint。
- 用 fake IndexedDB 测试精确替换 transaction：新增、更新、删除差集、空集合保护和 transaction 失败回滚。
- 测试 URL allowlist、`postMessage` requestId、后台 `sender.tab.url` 校验、错误来源和恶意 URL 被拒绝。
- 测试远端三态、插件请求被网络观察器再次捕获、快速连续切换、GET 乱序和二次确认不一致。
- 测试两轮抓取期间集合变化时仅 upsert 第二轮不删除、两轮稳定漏解析时完全不写入，以及跨域并发事件不会留下重复物理 key。
- 手动回归三个域名中当前可访问的域名；测试前使用专门的可逆收藏样本，不动用户已有重要收藏。

## 11. 发布与验证

首发继续沿用现有 GitHub Release / 手动安装渠道，先向 GAV Bus 已有用户和现有安装者发布一个明确标注的测试版。Chrome Web Store 和付费接入单独决策，不作为本功能上线的阻塞项。

上线后只跟踪最小指标：

以下指标仅上传不含内容身份的聚合计数，并以用户同意遥测为前提：

- 完成一次 MissAV 全量同步的人数。
- 官网收藏/取消事件成功同步到本地的次数与失败率。
- 插件发起官网取消的成功率。
- 7 天内再次打开管理页的用户比例。
- 愿意为“可靠闭环 + 后续整理能力”付费或留下联系方式的人数。

产品验证门槛不是安装量，而是至少出现一批用户反复依赖闭环，且有人明确愿意付费。若没有，应优先访谈和调整价值主张，而不是继续扩建同步内核。

## 12. 实施顺序

1. 先写纯函数与 fixtures：URL、endpoint、事件匹配、状态机。
2. 接入详情页只读 GET 和事件观察，验证不改变官网状态。
3. 接入官网候选事件、统一三态验证和本地 upsert/delete。
4. 接入插件管理页远端优先取消。
5. 实现全量精确替换和失败保护。
6. 完成自动测试、打包检查和手动三域回归。
7. 发布小范围测试版，收集行为数据和付费意向。

## 13. 尚未解决的问题

- MissAV 的 `/view` 响应字段尚未通过无副作用方式读取，只从页面代码确认读取了 `response.data.user` 和 `response.data.saved`；实现时应以最小只读请求验证响应 schema，并对未登录、缺失或非布尔值 fail closed。
- 详情页 endpoint 的 Alpine 字符串结构属于站点内部实现，需要 fixtures 和清晰的失效提示。
- 若用户明确要求“从插件重新收藏已删除条目”，需要先决定是否引入独立历史归档；这不应偷偷塞进第一版收藏 store。
- 付费方式、授权校验和成人内容相关的分发政策仍是独立产品议题，本设计不处理。

## 14. 我特别注意到的事项

- 页面代码会在网络请求返回前先翻转 `saved`，所以视觉状态不能作为成功依据。
- 影片番号与内部 API ID 不同，直接拼 endpoint 会产生危险的误操作。
- 146 页收藏让“部分失败、稳定漏解析或抓取期间集合漂移后仍删除差集”风险很高，必须在两轮结构完整且集合一致后才进入写 transaction。
- 当前 manifest 只给 `.ws` host permission，却已经声明 `.ai` 和 `.live` 的 content script match；B 方案必须同时修正权限，否则跨域行为会不一致。
- 当前 MissAV store 以 URL 为主键，官网切域可能制造重复项；第一版必须在业务逻辑层按 `videoId` 去重。
